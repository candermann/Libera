Überblick

Einzel-Admin-Webanwendung für das Schulbuch-Büro. Ein einziger Login (admin), kein Elternportal, kein Mehrbenutzer-Betrieb. Primäre Workflows:

  • Schüler anlegen, importieren (CSV), Klasse verwalten
  • Bücher und Lernmaterial pflegen (Bestand, Preise, Nutzungsjahre)
  • Bücher an Schüler verkaufen → Rechnung (PDF + E-Mail)
  • Bücher zurücknehmen → Gutschrift, Verrechnung mit neuer Rechnung
  • Saldo pro Schüler einsehen, Auszahlungen erfassen
  • Buchhaltungsexport, Mahnungen

Tech-Stack

Schicht Technologie
Backend Python 3.12, FastAPI, SQLAlchemy 2.x ORM
Datenbank SQLite (WAL-Modus)
Auth JWT (HS256), bcrypt-Passwort-Hashing, 7-Tage-Token
Frontend Vanilla JSX mit Babel Standalone (kein Build-Schritt)
PDF WeasyPrint (HTML-Templates via Jinja2)
E-Mail SMTP (konfigurierbar über Admin-Einstellungen)
Abhängigkeiten verwaltet mit uv + uv.lock

Kein Build-Schritt für das Frontend. Der Browser kompiliert JSX über Babel Standalone direkt beim Laden. Dadurch entsteht eine kurze Ladepause (~1–2 s), das System funktioniert aber ohne Node.js oder Webpack.

Lokale Entwicklung

Voraussetzungen

  • Python 3.12+
  • uv (Installationsanleitung)

Starten

cd backend

# Abhängigkeiten installieren
uv pip install -r pyproject.toml

# Server starten
SECRET_KEY=min-32-zeichen-langer-geheimschluessel-hier \
CORS_ORIGINS=http://localhost:8000 \
ADMIN_INITIAL_PASSWORD=adminpasswort \

Umgebungsvariablen

Variable Pflicht Beschreibung
SECRET_KEY Ja JWT-Signing-Key, mind. 32 Zeichen, zufällig generiert (openssl rand -hex 32)
CORS_ORIGINS Ja Kommagetrennte Liste erlaubter Origins, z.B. https://schulbuch.schule.de. Kein * erlaubt.
ADMIN_INITIAL_PASSWORD Nein Wird nur beim allerersten Start gelesen und als bcrypt-Hash in der DB gespeichert. Danach ignoriert. Standard: admin
DATABASE_URL Nein SQLAlchemy-Connection-String. Standard: sqlite:///schulbuch.db (im backend/-Verzeichnis). Im Docker-Image: sqlite:////app/data/schulbuch.db

Preislogik

Nutzungsjahr (NJ)

Jedes Buch-Inventar-Bucket hat ein nutzungsjahr:

Wert Bedeutung
0 Neu (kein Abschlag)
1–5 Gebraucht, 1–5 Schuljahre genutzt
6 Nur noch Schutzgebühr (ggf. 0)

Das Nutzungsjahr steigt um 1 pro vergangenem Schuljahr seit Kauf (Stichtag: 1. August).

Preisberechnung

Bucket-Preis (verkaufspreis_cents) = Basispreis × (1 − Abschlag_NJ%)
Wiederverkaufspreis                = Bucket-Preis + Rückgabe-Aufschlag  (nur NJ ≥ 1)
Gutschriftpreis bei Rückgabe       = Basispreis_zum_NJ_bei_Rückgabe     (ohne Aufschlag)
  • Der Rückgabe-Aufschlag (rueckgabe_aufschlag_cents) ist in den Admin-Einstellungen konfigurierbar.
  • Er wird im Bucket nicht gespeichert — er wird erst bei Verkauf (Frontend-Anzeige + Backend-Rechnung) addiert.
  • Die Gutschrift ist immer der reine Abschreibungspreis ohne Aufschlag → die Differenz (Aufschlag) verbleibt der Schule.

Abschläge (konfigurierbar)

Standardwerte (in den Admin-Einstellungen änderbar):

Nutzungsjahr Abschlag
1 0 %
2 10 %
3 20 %
4 30 %
5 40 %
6+ 100 % (nur Schutzgebühr)

Authentifizierung

  • Einzelner Benutzer: admin (kein Mehrbenutzer-System)
  • Token-Typ: JWT HS256, gültig 7 Tage
  • Passwort: bcrypt-gehasht, in einstellungen-Tabelle unter Schlüssel admin_password_hash
  • Erstes Passwort: Beim ersten Serverstart aus ADMIN_INITIAL_PASSWORD gelesen und gehasht gespeichert. Danach kann das Passwort über die Admin-Einstellungen im Browser geändert werden.
  • Passwort vergessen: Direkt in der SQLite-DB den Hash für admin_password_hash überschreiben (neuen Hash mit python -c "import bcrypt; print(bcrypt.hashpw(b'neuespasswort', bcrypt.gensalt()).decode())" erzeugen).

Datenbankmigrationen

Es gibt kein Migrationswerkzeug (kein Alembic). Stattdessen läuft bei jedem Serverstart init_db() → prepare_schema(), das alle notwendigen Schema-Anpassungen idempotent ausführt:

  • Neue Tabellen anlegen (CREATE TABLE IF NOT EXISTS)
  • Fehlende Spalten hinzufügen (ALTER TABLE ADD COLUMN)
  • Views neu erstellen
  • Indizes anlegen
  • Standard-Einstellungen seeden

Das bedeutet: einfach die neue Version deployen, der Server migriert sich selbst. Downgrade-Pfade sind nicht vorgesehen.

Tests

cd backend
uv pip install -e ".[dev]"

Tests liegen in backend/tests/. Sie verwenden eine In-Memory-SQLite-Datenbank und httpx als Test-Client. Kein Mock der Datenbank — Tests laufen gegen echte SQLAlchemy-Sessions.

Deployment (Docker)

Image bauen

Der Build-Kontext muss das Projektstammverzeichnis sein (damit Frontend und Backend beide erreichbar sind):

# Aus dem Projektstammverzeichnis ausführen:
docker build -f backend/Dockerfile -t schulbuch-verwaltung .

Container starten

docker run -d \
  --name schulbuch \
  -p 8000:8000 \
  -v /pfad/zum/daten-ordner:/app/data \
  -e SECRET_KEY="$(openssl rand -hex 32)" \
  -e CORS_ORIGINS="https://schulbuch.meine-schule.de" \
  -e ADMIN_INITIAL_PASSWORD="sicheresPasswort" \
  schulbuch-verwaltung

Das Volume /app/data enthält die SQLite-Datei schulbuch.db — dieses Verzeichnis regelmäßig sichern.

Empfohlene Produktionsarchitektur

Internet → nginx (HTTPS/TLS) → localhost:8000 (Docker-Container)

nginx übernimmt SSL-Terminierung (z.B. mit Let's Encrypt via Certbot). Die App selbst läuft nur auf HTTP.

Beispiel nginx-Konfiguration

server {
    listen 443 ssl;
    server_name schulbuch.meine-schule.de;

    ssl_certificate     /etc/letsencrypt/live/schulbuch.meine-schule.de/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/schulbuch.meine-schule.de/privkey.pem;

    location / {
        proxy_pass http://localhost:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

server {
    listen 80;
    server_name schulbuch.meine-schule.de;
    return 301 https://$host$request_uri;
}

Bekannte Einschränkungen

Thema Details
Einzelbenutzer Nur ein admin-Account. Kein Rollen- oder Mehrbenutzersystem.
SQLite Gut geeignet für diesen Use-Case (1 gleichzeitiger Schreiber). WAL-Modus aktiv für bessere Leseparallelität. Nicht geeignet für > 100 gleichzeitige Schreibanfragen.
Kein Frontend-Build Babel Standalone kompiliert JSX im Browser. Erste Ladezeit ~1–2 s. Kein Hot-Reload in Entwicklung.
PDF-Erzeugung Benötigt WeasyPrint mit System-Abhängigkeiten (libpango, libcairo etc.) — im Dockerfile bereits enthalten. Ohne WeasyPrint gibt der /pdf-Endpunkt HTTP 501 zurück; HTML-Vorschau funktioniert weiterhin.
E-Mail SMTP-Zugangsdaten müssen manuell in den Admin-Einstellungen im Browser eingetragen werden. Keine Autorisierung über OAuth/Google Workspace.
Keine Downgrade-Pfade prepare_schema() ist additiv — ein Rollback auf eine ältere Version kann zu Fehlern führen, wenn neue Spalten erwartet werden.
DSGVO Die App speichert personenbezogene Daten (Name, Adresse, E-Mail) von Schülern (Minderjährige). Betrieb nur auf EU-Servern; Verarbeitungsvereinbarung mit Schulträger empfohlen.
